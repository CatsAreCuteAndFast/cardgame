# CLAUDE.md

A single-player puzzle card game for the browser (phone portrait first), written in plain HTML/CSS/JS with no build step.
Repo: github.com/CatsAreCuteAndFast/cardgame (branch `main`).

## Commands

- Run the tests: `python test.py` (needs Chrome or Chromium). It serves the repo locally and runs `tests/index.html` in headless Chrome. The tests (`tests/tests.js`) check level parsing and validation (`levels/demo.json`, start-flipped tiles, starting counters, rejected levels), that every level in `levels/pack.json` loads, is at the current level version and has a saved solution that still wins (each move is checked as a legal tap sequence), that for the moves reachable within 3 plays on the demo and pack levels (up to 200 positions per step) the play changes only tiles in its preview and never changes the old state, card play and selection on the demo level, and bridge undo/redo, `solution()` and `checkSolution`.

## Game mechanics

**Core loop:** the player has a hand of cards and a play budget. Playing a card applies its effect to the board, uses one play and ticks every substrate. The level is won when every tile is flipped (`isWon`), and the phase becomes `won`. Otherwise, when the plays left reach 0, the phase becomes `over`. The status line shows plays left, won and out of plays.

**Board** (`game/types.js`, `game/state.js`): a W×H grid. Cells are flat indices (`width * row + col`, `toCell`/`toCoord`); level JSON and the UI use `[row, col]`.
- Tiles are `{type, flipped, link}` (`link` is a string group id or null). Tile types (`TILE_TYPES`): `basic`, `notflippable` (`canFlip: false`), `notswappable` (`canSwap: false`).
- Substrates sit under the tiles and do **not** move when tiles are swapped. The state keeps one counter per cell; the substrate types live in the level. `SUBSTRATE_TYPES` periods: 0 plain (always ready), 1 oneturn, 2 twoturn. A tile can be flipped only when its counter is 0 (`canFlipAt`). Each play ticks the counters: they count down and restart at the period after reaching 0, so they cycle. A counter starts at its period unless the level sets a starting value (0..period).
- Linked tiles: flipping one tile in a link group flips every tile in that group (the flip effect's `plan`).
- Starting state: the level's `flipped` lists the tiles that start flipped. The flipped state belongs to the tile, so it moves when tiles are swapped. A level where every tile starts flipped is rejected as already solved. `counters` sets the starting counter of individual substrates (0 = ready); each entry must be in bounds, listed once, and within 0..period.

**Cards**: `{effect, target, single_use, copy}`. `target` is kept in its JSON form (`{kind, coords}` or `{kind, count}`), and `copy` marks cards made by retarget.
- Effects (`EFFECTS` in `game/effects.js`):
  - `flip`
  - `swap`: two adjacent tiles, both of which must be swappable.
  - `retarget`: changes another card's targeting.
- Target kinds (`TARGETS` in `game/targets.js`):
  - `fixed` (coords): always acts on all its coords; you play it by picking any one of them (1 pick).
  - `from` (coords): pick 1 of the listed coords.
  - `any` (count): pick any `count` tiles.
  - `adjacent` (count): each pick must be adjacent to one already picked.
  - `card`: pick a card in the hand.
- Which effect takes which kind (`accepts`): flip takes any tile kind, retarget takes only `card`, swap takes only `adjacent` with count 2.
- Retarget turns `fixed` into `from` (and back) with the same coords. It **appends** the result to the hand as a new card with `single_use: true` and `copy: true`; the original card stays in the hand.

**Pure core** (`game/state.js`): a state is `{level, tiles, counters, hand, plays}` and is never changed in place. `applyMove(state, move)` returns a new state; a move is `{card, cells}` for a tile card (the picks) or `{card, target}` for retarget. `legalMoves(state)` lists every distinct move (picks covering the same set of tiles count once, and each set is explored once, because what can be picked next depends only on the set; a fixed card has one move). `stateKey(state)` identifies a position without the plays left, for searching.

**Controller phases** (`game/controller.js`): a game is `{state, phase}` and `handle(game, intent)` returns a new game. Intents are `{tap: "card", index}`, `{tap: "tile", cell}` and `{tap: "nothing"}`.
1. `idle`: tapping a card selects it, moving to `targeting` (`{index, picks}`).
2. `targeting`: the card is played once it has enough picks. Afterwards the phase becomes `won` if all tiles are flipped, `over` if the budget is used up, and `idle` otherwise. `won` and `over` ignore all input. While a card is targeting tiles, tapping another card switches to that card, and tapping the same card cancels. While a card is targeting a card (retarget), tapping a card is a pick, and taps on cards that can't be picked are ignored.

Tapping empty space cancels back to `idle`. Invalid tile picks are ignored. `selection(state, index, picks)` gives what a selected card can pick next (`candidateTiles`/`candidateCards`), what it would change (`preview`/`blocked`, from the effect's `plan`) and how many picks it needs.

**Web input** (`editor/board.js`, used by the tester page and the editor's Play tab; phone portrait is the intended way to play): taps work as above. On top of that, `attachPlayInput` turns gestures into the same bridge calls (`tapCard`/`tapTile`/`tapNothing`), so undo still counts one play per step. A drag (more than 10px) doesn't touch the game until the drop. A ghost card follows the finger. For a tile card, the board shows what the card would do: its options (`targeting` outlines), its changes (`preview`/`blocked`) and an orange dashed border (`.board.dragging`). These come from `bridge.peek(index)` and fade in through the CSS variable `--drag`, which goes from 0 at the drag start to 1 near the board's centre (`dragStrength`). For retarget, the cards it can change get the candidate border at full strength. Tapping a card skips all of this and selects it straight away. Holding a card still for 400ms (`LONG_PRESS`) shows the same options and changes at full strength, without the orange border and without selecting it, until the card is let go; moving the finger then turns the hold into a normal drag. The ghost is a clone of the hand card. Dropping a Fixed card on the board plays it (selects it, then picks its first candidate tile). Dropping another tile card on the board selects it, and its tiles are then picked by tapping or swiping. Dropping retarget on another card selects it and picks that card (or shakes the card if it can't be retargeted). Dropping anywhere else does nothing. Cards have `touch-action: pan-x`, so a drag must start upwards (a sideways move scrolls the hand). While an `adjacent` card has no picks yet, swiping from a tile to a neighbour picks both. A prompt line above the hand (`playPrompt`) says what to do next, with a Cancel button while a card is selected. The selected card shows a `k/N` badge when it needs more than one pick. Tapping a tile that can't be picked shakes it. `renderSnapshot` clears and rebuilds the board and hand itself (callers must not clear them first) and restores the window and hand scroll positions. The prompt row, status line and cards have fixed sizes, so the page doesn't change height as text changes. Cards (`renderCard`) have no text below the header. The header shows an icon and name in a colour chosen by effect and target kind (`CARD_FACES`, looked up as `effect:kind` and then `effect`): "Flip all" (Fixed, deep red), "Flip one" (ChooseFrom, orange-red), plain "Flip" for other kinds, ⇄ Swap (blue) and ✎ Retarget (purple). Below it is a mini-map of the board: filled squares for the tiles of a Fixed card, outlined squares for the choices of a ChooseFrom card, the whole board tinted with a ×N pill for `any` and a pill of N joined squares for `adjacent`. Retarget shows a filled card ⇄ an outlined card. Single-use cards have a dashed inner frame, and cards made by retarget have a "copy" tag. The old text label is kept as the card's `title`. Tiles (`renderCell`) have no text (the type id is the tile's `title`). Each tile is drawn in CSS as a key, after Drifl's "ember orange" tile designs: a face (`.face`) on a darker base (`.base`, with an orange `.base::after` that fades in when lit). `.tile` is a size container, so `cqw`/`cqh` inside it are tile units; corners are `--round` (12.5cqw) and the face is clipped with `clip-path: inset(0 round …)` (overflow clipping let animated children escape the rounded corners on some phones). Unflipped faces are purple (`--tile`); flipped faces are pushed in by 12/160 of the tile and lit orange (`--flipped`, with an inner glow). The light is `.light`, a circle covering the face, holding `.light-inner`, which carries the lit texture. The texture shows the type: basic tiles are grainy (`editor/grain.png`, drawn with `background-blend-mode: overlay` and stretched to the face width, so the grain scales with the tile like in the SVGs), notswappable tiles have wide white diagonal stripes (`.tile.ns`), and notflippable tiles are grainy with a darker face for now (`.tile.nf`). Tile highlights (candidate, targeting, picked, the editor's coord selection) are inset shadows on `.face::after`, so they show above the light. When a tile's flipped state changes in a one-play step (a play, undo or redo), it animates for 700ms (`FLIP_MS`). Flipping (`anim-on`): the face is pushed in over the first 31%, and from 23% the light circle scales up from the centre while `.light-inner` gets the inverse scale, so the texture stays still. Unflipping (`anim-off`) runs it in reverse. Only `transform` and `opacity` animate, so phones can run it on the GPU. The light keyframes are generated by `tools/light_keyframes.py` (21 scale steps of at most 1.2×, which keeps the counter-scale within 1%). `flipAnimations` keeps the last state and change time per board in a `WeakMap`, so a re-render mid-animation continues it (negative `--anim-delay`). Only steps within the same game animate: the snapshot's `game_id` changes on every `start()`, so loading, reset, restarting after an edit or switching level don't animate. A timed substrate's counter is a white number (no background, with a soft shadow) in the middle of the tile and moves with the face. Links still use the `L<n>` badge. The board previews the result: `preview` tiles get a dashed outline (filled with the colour they will flip to, for flip) and `blocked` tiles a ✕.

**Levels as JSON** (`game/level.js`): `parseLevel(data)` turns level JSON into a checked level (`{width, height, budget, tiles, substrates, links, flipped, counters, cards}` with per-cell lists) and throws an `Error` with a readable message if it's invalid; all validation lives there and in each target kind's `parse`/`check`. Format: `{"version", "budget", "tiles": [[id]], "substrates": [[id]], "links": [[[r,c],...]], "flipped": [[r,c],...], "counters": [[r,c,n],...], "cards": [{"effect", "target": {"kind", ...}, "single_use"?}]}`. `links`, `flipped` and `counters` are optional. The budget must be at least 1, coords must be exactly `[r, c]` (`[r, c, n]` for counters), `fixed` and `from` cards need at least one tile, and error messages number cards from 1, like the editor. `version` is the level format version (`LEVEL_VERSION`, now 1); a level without one counts as version 1, since that's the format every level had before versions existed. `upgradeLevel` (called by `parseLevel`, and by the editor on load, after a gist pull and on import) brings an older level up to date through `MIGRATIONS` one version at a time, and rejects a level from a newer game with a message to press Reload. When the format changes, bump `LEVEL_VERSION` and add the migration from the old version. The editor writes the version into new levels and exports, and `catalog()` reports it as `level_version`. Level files live in `levels/`. `levels/pack.json` is the tester pack: a list `[{name, folder?, level, solution?}]` in play order, the same format as the editor's "Copy all" and folder "Copy" exports. A solution is a list of moves, `{card, tiles: [[r,c], ...]}` or `{card, target}` with card indices counted from 0 in the hand at that moment; it is metadata about the level, kept next to `level` rather than inside it. `playMoves` (`game/state.js`) replays one and checks each move could be tapped (no moves after the level is won, card indices must be whole numbers). To publish levels to testers, put them in an editor folder, save a solution for each (win it in Play, then Save solution), press the folder's Copy, paste the result into `levels/pack.json`, then commit and push. `python test.py` fails if a pack level has no solution or its solution no longer wins.

**Demo level** (`levels/demo.json`): a 3×3 board, a budget of 1000 plays, and 5 cards: a fixed flip, a choose-from flip, an any-2 flip, a retarget and a swap. It uses mixed tile and substrate types and has one link group, {(0,1), (2,0)}.

## Architecture

**Layers:**
- `game/`: the rules as ES modules with no DOM access: `types.js` (tile/substrate registries, cell helpers), `targets.js`, `effects.js`, `level.js`, `state.js` (pure core) and `controller.js` (taps → moves).
- `editor/bridge.js`: the only interface between the pages and the rules (see `editor/`).
- `play/`: the tester page (`index.html`, `play.js`, `play.css`), live at https://catsarecuteandfast.github.io/cardgame/play/. It lists the levels in `levels/pack.json` and plays them with Undo/Redo/Reset and a "Next level" button after a win. There is no editing or sync. It reuses `../editor/editor.css` and `../editor/board.js`, imports `../editor/bridge.js`, and drives the same bridge calls as the editor's Play tab. Its Play screen fills the window height in one column: status and Undo/Redo/Reset at the top, the board sized to fit, the prompt line (with Cancel, or "Next level" after a win), and the hand pinned at the bottom as one row that scrolls sideways (`play/play.css`; `--top-h` is set from the header height in `play.js`). Both pages have a "↻ Reload" button in the header (`hardReload` in `editor/reload.js`, a plain script with no imports loaded before the modules, so it still works when a module fails to load; if the "Loading…" banner is still up when the page's `load` event fires, it changes to "Couldn't load the game. Press ↻ Reload."): it refetches the page and every same-origin file it loaded (script tags, stylesheets, and the imported rules modules, found through `performance.getEntriesByType("resource")`) with `cache: "reload"`, then reloads, because phones kept serving the old cached files after a deploy (`pack.json` is always fetched with `no-cache`). It keeps per-browser `cardgame.tester.solved` (names of solved levels, shown as ✓) and `cardgame.tester.last` in `localStorage`.
- `art/`: design files from Drifl, not loaded by the game. `art/tiles/ember-orange/` holds the tile designs (`grain-*` for basic tiles, `stripes-*` for notswappable; `-up` is unflipped, `-lit` is flipped) as 160×160 SVGs. The web tiles reimplement them in CSS (see Web input). `grain-texture.html` renders `editor/grain.png` (the regenerate command is in its comment): the SVGs' grain layer over 50% grey at 512px, which gives the same result as the SVG when overlaid on any face colour.
- `tools/`: helper scripts that aren't part of the game. `light_keyframes.py` prints the tile light keyframes for `editor/editor.css`.
- `editor/`: the web level editor, plain HTML/CSS/JS with no build step, made for phone, tablet (landscape) and PC use. A single breakpoint at 900px switches to the two-column layout. It is live at https://catsarecuteandfast.github.io/cardgame/editor/, served by GitHub Pages from `main` at the repo root (every push to `main` redeploys) (`.nojekyll` turns off Jekyll processing). All page scripts except `reload.js` are ES modules (`<script type="module">`) that import the rules statically, so there is no loading step. `editor/board.js` holds what is shared with `play/`: DOM helpers (`$`, `el`), board/hand rendering (`renderCell`, `renderSnapshot`), `playStatus`, `playPrompt`, `attachPlayInput`, `toast`, the colour tables and `catalog` (from the bridge). The editor is split by screen: `editor.js` (entry point: the shared `ui` state (tab, paint mode, brush, `pickCard`), `render`, `setTab`, `changed`), `store.js` (levels and folders in `localStorage`, level data helpers such as `blankLevel`, `formatLevel`, `normalizeLevel`), `sync.js` (gist sync), `levels.js` (Levels screen, Copy all, import), `edit.js` (Edit tab), `playtest.js` (Play tab, Save solution) and `dialogs.js` (text dialog, clipboard). The modules import `ui`/`render` from `editor.js` and only use them inside functions, so the circular imports are safe. The bridge provides `catalog()` (tile, substrate and effect ids, allowed target kinds and `level_version`, built from the registries), `validate(level)` (null or an error message), `upgradeLevel`, `solution()` (the moves played so far) and `checkSolution(level, moves)` (`{plays}` or `{error}`), and `start`/`tapTile`/`tapCard`/`tapNothing`/`undo`/`redo`/`snapshot` for playtesting, plus `peek(index)`, which returns, without selecting anything, the candidates and preview the card would have if it were selected. All of them take and return plain objects. The snapshot has `game_id` (counts `start()` calls). Its hand entries include `label`, `effect`, target `kind`, the full `target` and `copy`, and the snapshot has `preview`/`blocked`/`needed`. Undo and redo work per play: the bridge keeps the game after each completed play (a play is complete when the plays left change), so undo just steps back. Undo also drops a half-made selection, and making a new play clears the redo stack. Levels are stored in that browser's `localStorage`: `cardgame.levels` (each has `id`, `name`, `folder` (folder id or null), `updated`, `data`, and optionally `solution`) and `cardgame.folders` (`id`, `name`, `collapsed`). Optional sync between devices goes through a secret GitHub gist holding `cardgame-levels.json` (`{version: 1, updated, levels, folders}`), called straight from the browser. The Sync dialog takes a gist-scoped token and a gist id; a blank id creates the gist from this device's levels. Each device keeps `cardgame.sync` (`token`, `gistId`, `remoteUpdated`, `dirty`); the token never leaves that browser except to api.github.com. The editor pulls on load and whenever the tab becomes visible, and pushes about 2 s after a change to levels or folders (and when the tab is hidden). A push first re-reads the gist. If the gist's `updated` differs from `remoteUpdated` while this device also has unsynced edits, a confirm asks which side wins; there is no merging. `localStorage` stays the working copy, so offline edits push later. The open level (`cardgame.current`) is per device and not synced. Folders are one level deep. The Levels screen sorts folders and levels by name with natural ordering, so "Level 2" comes before "Level 10". Deleting a folder moves its levels to Ungrouped. "Copy JSON" exports one level in the same compact layout as `levels/demo.json`. "Copy all" and a folder's "Copy" export `[{name, folder?, level, solution?}]`, and "Import JSON" accepts that list (recreating folders by name, keeping solutions) or a single level. After a win, the Play tab's prompt row shows "Save solution", which stores the moves played on the level record; the Edit tab shows below the validation whether the saved solution still wins the level as it is now (`renderSolution`).

**Play flow** (`editor/bridge.js`): a tap in `board.js` → `tapCard`/`tapTile`/`tapNothing` → `handle(game, intent)` → `snapshot()` (built with `selection`) → `renderSnapshot`.

**Conventions:**
- Plain JS with no build step, all ES modules. The rules live under `game/`; page code shares helpers through `editor/board.js`. Module top-level code must not use another module's bindings (keep side effects in each page's `init`), because the editor modules import each other in a cycle.
- Registries are plain objects keyed by id (`TILE_TYPES`, `SUBSTRATE_TYPES`, `TARGETS`, `EFFECTS`); their key order is the editor's palette order, and the editor builds its palettes from `catalog()`.
- Each effect and target kind is one object holding all its behaviour, so a new one is added in one place.
- Rules code never changes a state in place; functions return new states.
- Very few comments; a short one above each module or non-obvious function.

**Adding a new effect** means adding an entry to `EFFECTS` in `game/effects.js` (`onTiles`, `accepts`, and either `canPick`/`plan`/`apply` for tile effects or `canModify`/`apply` for card effects). The editor picks it up through `catalog()`; check `SAMPLE_TARGETS` in `editor/bridge.js` if it needs new target params, and add a card face in `CARD_FACES` (`board.js`).

**Adding a new target kind** means adding an entry to `TARGETS` in `game/targets.js` (`onTiles`, `needs`, `isCandidate`, `resolve`, `parse`, `check`, `describe`), a sample in `SAMPLE_TARGETS` in `editor/bridge.js`, and `KIND_LABELS`/`defaultTarget`/the card details UI in `editor/editor.js` (and the card mini-map in `cardArt`, `board.js`).

## Known issues / loose ends (not yet confirmed as intended)

- The flip effect's `plan` checks `canFlipAt` only on the picked tile. The other tiles in its link group flip even if they are notflippable or their substrate is not ready.
- Flip's `canPick` always returns true, so a blocked tile can still be picked. The flip then does nothing but still uses up a play. This may be the intended "changed flip behaviour" from commit 5ce40f2.
- Retarget appends a new card instead of replacing the targeted one, so the hand keeps growing.
- The demo level (`levels/demo.json`) can't be won: (0,2) and (2,1) are notflippable and not linked.
- No solver for now. A breadth-first solver was added in 9f9aa4f and removed again: it managed only about 2,000 positions/s, which was too slow, and the current levels are easy enough without one. Drifl wants a faster one later that can handle 3×3 boards needing 10 or more plays. The JS core is built for it (`legalMoves`, `applyMove`, `stateKey`); 9f9aa4f is a useful reference for the editor wiring (a module Web Worker, a solver panel, and "Step through" through the redo stack).
